# 中国诗歌时空图谱 · 产品与技术设计

> 从地域与时间两个维度，系统映射中国诗人与作品的创作背景。
> 目标：可商用、可扩展、学术严谨。

---

## 一、项目定位

### 核心问题

一首诗不是孤立文本。它诞生于**特定的人、在特定的地方、于特定的时间、因特定的事**。
本项目的目标，是把这四重要素结构化关联起来，让用户能：

- 沿**地理**看：某个地方，历史上谁在这里写过什么
- 沿**时间**看：某个时期，诗人们都在写什么
- 沿**人物**看：一个诗人的一生轨迹与各地创作分布
- 沿**情境**看：这首诗为什么在此地此时被写出来

### 差异化价值

市面上已有的诗词产品（古诗文网、搜韵等）**普遍只有文本**，缺少时空维度的结构化考据。
本项目最大的价值不在诗库本身（诗库可白得），而在于**「作品—地点—时间—情境」的关联数据及其溯源体系**。

⚠️ 这一判断决定了整个设计的重心：**力气应该花在考据数据层，而不是前端花活上。**

---

## 二、最关键的约束：地理位置精度必须分级

用户最初要求「精确到现在的乡镇级别」。经过史料调研，必须明确：

**古诗创作地的史料记载，绝大多数只到「州」「县」一级。**

例如《春望》只记「长安」，《念奴娇·赤壁怀古》只记为黄州赤鼻矶。
真正的乡镇级（如「巩县东二里」）极为罕见。

### 处理原则

| 精度层级 | 含义 | 示例 | 坐标策略 |
|---|---|---|---|
| `site` | 具体遗址 | 成都杜甫草堂 | 实测精确坐标，`isCentroid: false` |
| `township` | 乡镇级 | 史料明确记载乡镇 | 乡镇中心坐标 |
| `county` | 县级 | 「巩县」「密州诸城」 | 县城中心，**标记为中心点** |
| `prefecture` | 州府级 | 「长安」「扬州」 | 城市中心 |
| `province` | 省级 | 「江南东路」 | 省会坐标 |
| `approximate` | 大区域 | 「塞外」「岭南」 | 区域中心，**界面须明确弱化** |

**硬性规则**：`isCentroid: true` 的点在界面上必须弱化呈现（如半透明、虚线圈），
不得让用户误以为那是精确遗址位置。这是学术诚信，也是商用产品的免责底线。

## 三、架构：四层分离

```
① 采集层 raw/   →  ② 考据层 core/  →  ③ 派生层 derived/  →  ④ 应用层 web/
   原始快照           人工考据数据         构建期生成          展示与交互
   不可修改           唯一真相源           可随时重建          只读消费
```

### 为什么这样分层

1. **采集层与考据层分离**：外部数据可能被污染或格式变动，考据结论是我们的核心资产，
   必须独立存储，不因外部源变化而丢失。
2. **派生层不入库**：索引、聚合、地图打点全部可由考据层重新生成。
   只要考据数据在，任何索引损坏都能重建。这让系统天然抗腐坏。
3. **应用层零逻辑**：前端不做任何数据推断，只消费烘焙好的 JSON。保证展示行为可预测。

### 因为并入静态导出的 blog，架构必须"烘焙化"

现有 blog 是 `output: 'export'` 纯静态站点，**没有服务端**。因此：

- ❌ 不能有数据库查询 API
- ✅ 所有数据在**构建期**预生成为静态 JSON 分片
- ✅ 前端按需 `fetch` 对应分片

这反而带来了优势：**零服务器成本、天然 CDN 加速、可直接商用部署**。

## 四、数据模型

### 核心创新：用「考据断言」代替「事实字段」

传统做法是给每首诗直接挂 `location` 和 `date` 字段。这个做法有一个致命缺陷：

> 《静夜思》写于何处？扬州说、安陆说、不可考说——三者并存。
> 如果只有一个 `location` 字段，要么强行选一个（学术不诚实），要么丢弃其余（信息丢失）。

本项目引入 **Assertion（考据断言）** 实体：

```ts
interface Assertion {
  workId: string;
  placeId?: string;        // 创作地
  date?: HistoricalDate;   // 系年
  circumstance?: string;   // 创作情境
  rationale: string;       // 判断依据（必填！）
  sources: Source[];       // 文献来源（必填！）
  confidence: 'A'|'B'|'C'|'D';
  groupId?: string;        // 异说分组
  isPrimary?: boolean;     // 是否主流说法
}
```

**一条断言 = 一种说法。** 同一作品可挂多条互斥断言，用 `groupId` 归组，
前端并列展示为「异说」，由用户自行判断。

### 置信度分级

| 等级 | 含义 | 判定标准 |
|---|---|---|
| **A** 确定 | 作者自述、同时代明确记载、实物佐证 | 如《水调歌头》词序自述「丙辰中秋…作此篇」 |
| **B** 较可靠 | 权威年谱、正史、学界主流共识 | 如《春望》系于至德二载 |
| **C** 存疑 | 古今说法不一，或仅晚出记载 | 如《静夜思》作地 |
| **D** 传说 | 民间附会、明显时代错置 | 如某些「李白醉草吓蛮书」类传说 |

### 强制溯源

**每条断言必须有 `rationale` 和 `sources`，否则构建失败。**

这是可商用产品的合规底线：任何考据结论都必须能追溯到文献，
否则一旦被质疑，整个数据集的公信力都会受损。

### 数据完整性红线（经历过真实事故后固化）

这几条是实打实踩过坑才写下的，**不是理论洁癖**：

1. **零数据必须报错，不得静默通过。**
   曾出现过路径推导错误导致「载入 0 条数据，却报告校验通过，并写出 5 个空文件」的事故。
   现在 `validate.ts` 有 `empty-dataset` 硬性错误，且所有路径基于
   `fileURLToPath(import.meta.url)` 推导，与执行目录无关。

2. **禁止「借地名凑数」。**
   曾把李白的「安陆」断言错误地挂在「池州」上。地名词表是共享资产，
   一个错误地点会同时污染多位诗人、多个作品、以及地图与轨迹。
   规范做法是**先在地名词表里建正确条目，再引用其 id**。

3. **禁止示例占位数据流入正式集。**
   曾出现苏轼祖籍写着「巩县（示例占位）」的情况。占位数据一旦混入，
   会随构建产物一路发布到线上，且因为"校验通过"而极难被发现。
   现在要求：宁可暂缺该字段，也不写错。

4. **籍贯与生平事件也是地图价值。**
   地图打点早期只由「作品断言」驱动，导致眉山（苏轼籍贯）、江油（李白出生地）
   等重要地点因"暂无作品"而缺席。现在打点由**作品 + 籍贯 + 生平事件**三者共同驱动，
   并在 `DerivedMapPoint` 上以 `isBirthplace` / `eventCount` 显式标注。

## 五、数据源方案

### 已确认可用（MIT / 开放许可，可商用）

| 数据源 | 内容 | 许可 | 用途 |
|---|---|---|---|
| **chinese-poetry** | 5.5万唐诗 + 26万宋诗 + 2.1万宋词 | **MIT** ✅ | 文本底本 |
| **CBDB** 哈佛中国历代人物传记库 | 65万历史人物传记数据 | 学术开放，需引用 | 生卒年、籍贯、仕宦 |
| **CHGIS** 复旦/哈佛历史地理系统 | 历代行政区划与地名 | 学术开放，需引用 | 古今地名对照 |

### 需谨慎（版权受限，商用需授权）

| 数据源 | 说明 |
|---|---|
| 中华书局点校本《全唐诗》《全宋词》 | 整理成果有版权，**不可直接复制** |
| 各类现代注本、鉴赏辞典 | 专有内容，商用需授权 |
| 学术论文中的考据结论 | 可引用观点，但需注明出处，不可大段复制 |

### 合规策略

1. **文本用公有领域底本**：诗词原文本身属公有领域（作者已故逾千年），可自由使用。
   但**现代标点、校勘、注释**有版权，须自行处理或使用开源版本。
2. **考据结论标注来源**：引用学界观点时标注文献，属合理使用范畴。
3. **不出售考据数据本身**，以产品功能形式提供服务。
4. **保留所有 sources 字段**，对外提供溯源能力，这既是合规也是卖点。

## 六、技术栈

### 前端（并入现有 blog）

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | Next.js 16 App Router | 与现有 blog 一致，零迁移成本 |
| 语言 | TypeScript 5.9 | 强类型保证数据契约 |
| 样式 | CSS Modules | 项目已有约定，**禁用 styled-jsx** |
| 地图 | **MapLibre GL JS** | 开源免费可商用（Mapbox GL 商用需付费） |
| 底图 | 高德/天地图 WMTS 或 MapTiler | 国内访问速度，注意地图合规 |
| 图表 | 轻量自绘 SVG | 避免引入重型图表库 |

> ⚠️ **地图合规**：中国大陆境内提供地图服务须使用有测绘资质的数据源，
> 未经批准不得使用境外地图。正式上线前必须确认底图来源合规。

### 数据管线（Node 脚本）

| 工具 | 用途 |
|---|---|
| `tsx` | 直接运行 TypeScript 脚本 |
| `ajv` | JSON Schema 校验 |
| 自定义校验器 | 引用完整性、坐标范围、溯源完备性 |

### 产物形态

```
data/derived/
├── manifest.json          总清单（含统计与告警）
├── poets-index.json       诗人列表（轻量，供索引页）
├── map-points.json        地图打点（按作品数排序）
├── timeline.json          时间轴（按十年分桶）
├── themes.json            主题聚合
├── poet/<id>.json         诗人详情（含作品/事件/轨迹）
└── work/<id>.json         作品详情（含全部异说）
```

## 八、质量保障

```bash
cd poetry-atlas
npm run build     # 校验 + 生成派生数据，有 error 则中止
```

**必过检查项**：

1. 所有 id 唯一
2. 所有外键引用存在（作品→诗人、断言→作品/地点/事件）
3. 坐标在中国境内合理范围 [73-136, 3-54]
4. **每条断言都有 rationale 和 sources**
5. 异说组内不能全部标记为 A 级
6. 无孤立地点（定义了但无人使用）

## 九、关键风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 考据工作量大 | 是最大瓶颈 | 从 A/B 级确定案例切入，C 级异说后补 |
| 地理精度不足 | 用户期望落差 | **分级透明标注**，把限制转化为专业性的体现 |
| 史料争议 | 公信力受损 | 异说并存 + 强制溯源，让分歧可见而非掩盖 |
| 地图合规 | 无法上线 | 提前确认底图资质，必要时降级为示意地图 |
| 数据版权 | 商用风险 | 只用公有领域底本 + 开源数据集，考据结论标注来源 |
